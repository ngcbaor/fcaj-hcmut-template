During the 7-week internship at the First Cloud AI Journey (FCAJ) program from June 15 to July 31, 2026, I was responsible for developing the entire Go backend service within the awsplace project — a collaborative pixel-canvas application deployed on AWS ECS Fargate. The work covered backend API development, real-time WebSocket handling, DynamoDB integration, EFS shared storage configuration, and CI/CD pipeline setup using AWS CDK and GitLab CI.

Looking back, there are areas where I performed well and areas where I still have room to grow. Rather than overstating what went right or downplaying what needs work, I want to give an honest picture of where I stand after this experience.

### What went well

- Gained hands-on confidence working with AWS services end-to-end, from account setup to production deployment on ECS Fargate. This was a significant step up from the classroom-level understanding I had before.
- Developed a working habit of reading official documentation first and experimenting in a sandbox before implementing changes in the main codebase. This saved a lot of debugging time in the later weeks.
- The blog writing process helped me articulate technical concepts more clearly. Explaining something in writing forces you to actually understand it, not just get it to work.
- Participating in 4 community events (2 online, 2 in-person) broadened my perspective beyond just coding — hearing from industry professionals about career strategy, security architecture, and AI-driven development was genuinely eye-opening.

---

### Needs Improvement

- **Time estimation**: I consistently underestimated how long infrastructure tasks would take, especially when dealing with IAM permissions and networking configurations. Getting better at scoping work realistically is something I need to work on.
- **Verbal communication under pressure**: While I can write technical content reasonably well, presenting ideas on the spot during team discussions or Q&A sessions is still uncomfortable. This is partly a confidence issue and partly a preparation issue.
- **Deeper architectural thinking**: I can implement features and follow established patterns, but when it comes to making architecture-level tradeoff decisions (e.g., choosing between synchronous vs. event-driven patterns for a specific use case), I still rely heavily on mentor input rather than reasoning through the options independently.
- **Discipline around documentation**: I sometimes wrote code first and documented later, which led to gaps in comments and README updates. Building a habit of documenting as I go would make handoffs smoother.
